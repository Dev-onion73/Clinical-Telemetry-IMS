Yes. We should review **every duration-bearing span we've introduced so far**, including Encounter and Episode, and explicitly define the allowed start/end reasons. This should become the lifecycle vocabulary that the backend and IncidentRelay integration implement.

One caveat: OpenTelemetry's current model defines spans with start/end timestamps and timestamped events, while its 2026 guidance is moving new event implementations toward log-based events correlated with traces. So our **domain model should define lifecycle events abstractly**, without coupling the domain to `Span.AddEvent()` specifically. ([OpenTelemetry][1])

| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |

Its start/end reasons describe why the overall encounter exists and why it ended.                                         |
| **Episode**                         | Alarm acknowledged while no Episode exists; manually initiated clinical activity; scheduled procedure; unplanned procedure; other clinically meaningful activity requiring an Episode | Clinical activity completed; procedure completed; clinical issue resolved; episode cancelled; episode terminated/closed by authorized clinician | Child of Encounter. ### The hierarchy rules remain unchanged

The table describes **what can happen inside the trace**, while parentage remains separately constrained.

The fundamental structure is:

```text
ENCOUNTER
└── EPISODE
    ├── INCIDENT
    ├── INCIDENT
    ├── OBSERVATION
    │   ├── JOURNAL EVENT
    │   └── INCIDENT
    ├── MEDICATION
    ├── ASSESSMENT
    ├── INTERVENTION
    └── PROCEDURE
```

Multiple incidents remain siblings regardless of when they occur:

```text
EPISODE
├── INCIDENT A   08:00–08:04
├── INCIDENT B   10:15–10:22
└── INCIDENT C   14:30–14:35
```

**A later alarm never becomes a child of an earlier alarm merely because it happened later.**

### Every span gets two lifecycle records

For any duration-bearing span:

```text
START EVENT
    │
    │ start_reason
    ▼
┌─────────────────────┐
│       SPAN          │
└─────────────────────┘
    │
    │ end_reason
    ▼
END EVENT
```

So, for example:

```text
EPISODE
│
├── EPISODE_STARTED
│     reason = incident_acknowledged
│
│     ───── Episode duration ─────
│
└── EPISODE_ENDED
      reason = clinical_resolution
```

And:

```text
INCIDENT
│
├── INCIDENT_TRIGGERED
│     reason = spo2_threshold_exceeded
│
│     ───── alarm waiting period ─────
│
└── INCIDENT_ACKNOWLEDGED
      responder = DR-RAJESH
```

### One important distinction

**Start/end reason ≠ current status.**

For example:

```text
episode.status = ACTIVE
episode.start_reason = INCIDENT_ACKNOWLEDGED
```

and later:

```text
episode.status = CLOSED
episode.end_reason = CLINICAL_RESOLUTION
```

The status describes **where the object currently is in its lifecycle**.

The reason describes **why it entered or left that state**.

That distinction should exist in both PostgreSQL's domain model and the trace representation.

### The model we should freeze

I would reduce the rules to these invariants:

1. **Every duration-bearing clinical object has a start reason.**
2. **Every duration-bearing clinical object has an end reason.**
3. **Every start and end has a timestamp.**
4. **Every lifecycle boundary produces a point-in-time trace occurrence.**
5. **A span represents the interval; the lifecycle occurrences explain its boundaries.**
6. **Events do not have an end reason because they are instantaneous.**
7. **Incident spans remain open until condition-clear, dismissal, or acknowledgement.**
8. **Acknowledging an Incident outside an Episode initiates an Episode.**
9. **Acknowledging an Incident already inside an Episode only ends that Incident span.**
10. **Incidents never structurally contain other Incidents.**
11. **Temporal ordering never creates parent-child relationships.**
12. **Causal/related relationships between independent spans use links or explicit references, not parentage.** OpenTelemetry supports links specifically for related spans that don't fit the parent-child tree. ([OpenTelemetry][1])
13. **An Episode is the clinical boundary for its internal activity.**
14. **Encounter is the root clinical span for the encounter.**

I would consider this the **Clinical Trace Lifecycle Contract**. Before implementing IncidentRelay or the backend, we should probably turn this table into the formal Phase 02.5/Phase 03 domain specification, because the allowed reasons will directly determine our database enums, API operations, IncidentRelay integration, and trace-generation logic.
